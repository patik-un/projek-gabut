# Wedding photobooth backgrounds

User approved a background applying from start through photobooth results, including fullscreen, with Elegant Cream, Soft Pink, Floral presets, custom JPG/PNG upload, and adjustable darkness. Scope is UI background only: admin/other app menus, camera pixels, composite exports and print output are unchanged.

Preserve existing default appearance until an operator chooses a theme. Add a Tampilan Photobooth card in the existing admin Photobooth tab, with preset choices, preview, darkness 0–85%, saved custom image thumbnail/reselection and upload. Explicit apply saves theme/darkness; successful image upload saves and applies it, with clear UI copy. Settings/assets persist in writable backend app data, never localStorage base64. A previous appearance survives failed saves/uploads. Disable overlapping mutations and reject stale initial loads.

Backend GET/POST `/photobooth/appearance` returns `{theme,dim,image_url,has_image}`; theme values default/elegant/pink/floral/custom, dim integer0–85 default35. POST configuration accepts theme/dim only and requires an existing asset for custom. POST `/photobooth/appearance/image` accepts data_base64 and optional dim. JPEG/PNG only, decoded size ≤8MiB, ≤24M pixels; metadata-stripped JPEG output with white alpha background, aspect-preserving long-edge limit4096. Bounded request JSON≤12MiB. Store assets as immutable `booth_background_<uuid>.jpg` in existing watermark static folder and config in `booth_appearance.json`, with atomic writes and lock. Response URLs are root-relative `/watermark-files/booth_background_<uuid>.jpg`; never accept client paths/URLs. Corrupt/missing config/image falls back safely without overwriting operator data on GET.

Frontend keeps appearance independent of print/layout settings. A separate backdrop layer is mounted only in photobooth and never inside an exported canvas. Themes use code-native gradients/vector floral decoration. Main photobooth shells become transparent while text, actions, camera, editor and preview surfaces keep readable contrast. Admin preview shows the proposed appearance before applying. Request failure is actionable; old settings remain; retry and reconnect reload are supported.
